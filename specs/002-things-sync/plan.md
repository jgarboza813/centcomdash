# Implementation Plan: Sync with Things

**Branch**: `main` | **Date**: 2026-10-31 | **Spec**: [spec.md](spec.md)
**Input**: `specs/002-things-sync/spec.md`

## Summary

Enable the existing button to read Things Today tasks tagged exactly ❗, derive new weights
from XL/L/M/S tags, and reconcile linked completion with Things as authority. Extend the local
React/Express/SQLite application; no separate service, cloud integration or Things writes.
The current checkmark CSS edit is independent and must not be overwritten.

## Technical Context

**Language/Version**: Existing strict TypeScript, Node 24, React 19 and Express 5; a local third-party jaydenk/things-api Python service reached through Node fetch.
**Primary Dependencies**: Existing Zod, better-sqlite3 and Node fetch; external Python 3.12+ things-api
service with things.py. Pin tested service/library versions during the compatibility check. Adapter interface isolates platform access from merge logic and test fixtures.
**Storage**: Existing SQLite aggregates and mutation receipts, plus source links and per-day
last-success metadata in a transactional user_version 2 migration. Existing plan JSON schema
and fixed-budget-v1 calculations remain unchanged.
**Testing**: Vitest for filtering/merge and transactional API tests; Playwright for explicit
button triggers and UI states; separate opt-in real-Mac validation. Tests never automate the
user's Things library by default.
**Target Platform**: Same Mac as Things 3; loopback browser/API. The Things API service must be running on 127.0.0.1:5225; its database
reader does not depend on a Things GUI automation session. Validate behavior with the installed
Things version; no automatic service/app launch or startup source reads.
**Project Type**: Incremental feature in the existing single npm package.
**Performance Goals**: Ten valid selected tasks imported in under two minutes including
normal user interaction; one source operation at a time; adapter deadline 30 seconds and
4 MiB output bound. Exceeding bounds fails explicitly without partial import/truncation.
**Constraints**: Button-only invocation and manual retries; exact tag matching; no background
reads, health probes of Things on startup, direct Things database access in Central Command or source mutations. The accepted third-party
service reads the database through things.py; its compatibility risk is recorded in research.md.
**Scale/Scope**: One local user, today's editable plan. Already linked tasks are resolved
outside Today to find completions. Past-day backfill and sync on other dates are excluded.

## Execution Design

1. First pin and validate the local Things API service in read-only mode: /health, /today,
   /todos/{id}, exact tags, completed and missing/trashed lookup, payload completeness and
   matching Things database version. Record sanitized response schemas as fixtures. Do not run it merely to load the dashboard or execute mocked tests.
2. Button handler captures and reserves the selected date before awaiting anything; disable
   its editing/lifecycle actions during save draining. After flush, capture that date’s
   acknowledged revision and stable operation ID before requesting sync. A failed flush prevents all Things access.
3. Server validates input and checks matching committed receipts first, before date/lifecycle/
   revision eligibility. Return exact replay without source access even after midnight or
   finalization. Only requests without a receipt reject non-today/finalized/stale state. Acquire a per-day
   operation guard across tabs; reject overlaps. Read tagged Today candidates and tracked IDs
   via one adapter operation, validating the complete response before any database write.
4. Pure merge appends valid new tasks in source order, matches only source IDs, retains manual
   tasks, preserves weights, refreshes readable titles, and makes source completed/open status
   authoritative. Readable open/completed linked tasks reconcile even outside Today; rescheduled open tasks
   are also reported unresolved for Today membership, without overriding source completion
   authority. Missing/canceled/trashed entries are
   unresolved, never inferred complete. Removed ❗ tag does not unlink an existing commitment.
5. Transaction rechecks revision, editable status and New York today at commit. Save plan,
   links, result receipt and last-success metadata together. All-skipped/empty/no-change reads
   are successful with counts; they still produce a receipt and success timestamp/revision.
6. Return the new day envelope and counts. Update the captured date's cache and refresh derived
   views, never replace another date after navigation. UI may navigate during the request;
   it must retain the original operation context. No effect/timer/focus listener starts sync.

## Third-party service configuration

Central Command reads CENTCOM_THINGS_API_URL (default http://127.0.0.1:5225) and
CENTCOM_THINGS_API_TOKEN server-side. Restrict URL to that loopback host/configured port,
reject credentials/query/path overrides and redirects, and never expose the token to Vite,
HTML, browser requests, logs or Git. Calls are GET-only; the service can support writes but
Central Command cannot request them.

Run the service with THINGS_API_HOST=127.0.0.1 and a bearer THINGS_API_TOKEN. Ensure
THINGS_AUTH_TOKEN is absent from effective environment/config so write mode is disabled;
verify /health reports read=true/write=false during the explicit compatibility check. Do not
reuse the setup wizard's detected Things URL write token. No service installation or live
compatibility probe was executed by this planning revision.

## Uncertain-response recovery and source date alignment

Use the explicit recovery-only endpoint in contracts/sync-api.md when the user next activates
the same button after an uncertain response. Recovery stays available for its original date
regardless of midnight/finalization, and never reads Things or starts another sync. A missing
receipt is not permission to read again. Keep per-date recovery context and newer acknowledged
revisions intact; no automatic recovery/polling.

Configure the external service process with TZ=America/New_York and verify that the pinned
Things reader's Today definition honors that zone at both sides of New York midnight/DST.
Do not assume the Mac's current timezone or service endpoint name establishes this. Record
verified semantics in compatibility evidence. Unknown/mismatched source date configuration
blocks fresh sync with THINGS_DATE_MISMATCH rather than importing the wrong day's candidates.
Clock/date checks at commit still apply; receipt recovery does not require source access.

## Today and This Evening scope

“Today” source membership includes both Things Today and its This Evening section. The pinned
things-api /today endpoint returns both; no separate evening endpoint or bucket exclusion is used.
Both sections use the same ❗ marker, weight rules, identity and completion reconciliation. The
synthetic pinned-library check in tools/things-api/verify_reader.py verifies both source buckets;
reader and browser fixtures cover evening import through the normal explicit button action.
